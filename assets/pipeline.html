lectoria · pipeline

From a document to multilingual audio in seven stages

Each stage is a small interface with a single responsibility. The orchestrator (runPipeline) wires them together and fans out per target language at the script stage. Pass RunOverrides to swap any stage for your own implementation.

Input + parse
LLM (Azure OpenAI)
Audio (Azure Speech)
Output
step 1

ingest

Pulls bytes from a path, folder, or URL.

→ SourceFile
step 2

parse

PDF / DOCX / MD / HTML → normalized document with sections + paragraphs.

→ Document
step 3

script

Generates the source-language script (podcast / conversational / verbatim / dialogue). Chunks by section to dodge per-minute TPM caps.

→ PodcastScript
step 4

translate

Re-renders the script in every target language; preserves style + speaker tags.

→ PodcastScript[]
step 5

synthesize

SSML per utterance, voice dispatch per speaker, segment-by-segment Azure Speech calls.

→ SynthesizedAudio
step 6

package

Wraps the MP3 with ID3 tags + chapter markers derived from segment offsets.

→ Episode
step 7

distribute

Writes the episode + updates the RSS feed (or your custom distributor).

→ Feed

Cross-cutting concerns

  • Logger — human-readable progress (default no-op).
  • onProgress — structured events per stage for progress bars / telemetry.
  • AbortSignal — cancel any long-running stage mid-flight.
  • LectoriaAuth — credential / apiKey / default. Threaded through both Azure clients.

Pluggable surfaces

  • ScriptModel — swap Azure OpenAI for OpenAI direct, Anthropic, or a stub for tests.
  • TtsProvider — swap Azure Speech for any TTS provider that emits MP3.
  • Packager — replace the default ID3 packager for OGG, WAV, or chaptered M4A.
  • Distributor — write to S3, upload to Azure Blob, post to a webhook.
